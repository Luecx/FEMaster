\chapter{Model Definition}
\label{chap:model-definition}

Model definition describes how finite-element topology is organized before properties, loads, constraints, or analysis procedures are applied. FEMaster supports two equally valid styles. A compact flat model places nodes and elements directly in the root context and is sufficient for many calculations. A structured model places reusable topology in named Parts and creates one or more rigid Instances. The latter is particularly useful for assemblies, repeated components, independent local identifier spaces, and models imported from Abaqus.

The distinction is semantic rather than merely syntactic. A Part stores sparse local node and element identifiers. An Instance references that Part and stores only its rigid placement. The source topology is not copied or transformed when the instance is parsed. During \texttt{Model::compile()}, every instance is expanded into dense assembly storage, local identifiers are mapped to compiled identifiers, and node coordinates are transformed. This creates a clean one-way boundary between user-facing topology and solver-facing data.

\section{Model organization}

\keywordpage{MODEL}

\cmd{MODEL} is an optional native FEMaster root marker. It gives a deck an explicit top-level model name and can improve readability in generated input, but a native FEMaster deck does not require it. Omitting \cmd{MODEL} does not change the default Part mechanism or the compile boundary. The Abaqus reader has no corresponding \cmd{MODEL} keyword; an Abaqus deck simply starts with its root-level definitions.

The command is allowed at root level. Its \key{NAME} parameter is optional and descriptive. It does not create a second nested finite-element model and cannot be used to switch between multiple models in one analysis run. In practice, use it when a deck benefits from an explicit title-like structural marker, while keeping \cmd{HEADING} for free-form descriptive text.

\begin{keywordparameters}
\key{NAME} & optional & Descriptive name of the top-level FEMaster model. \\
\end{keywordparameters}

\syntaxheading

\begin{syntax}
*MODEL, NAME=BRACKET_MODEL
\end{syntax}

No data lines follow the command. Geometry may immediately follow at root level, or the deck may proceed with explicit Part definitions.

\exampleheading

\begin{dialectexamples}
\begin{femasterdeck}
*MODEL, NAME=BRACKET_MODEL
*NODE
1, 0., 0., 0.
2, 10., 0., 0.
\end{femasterdeck}
\begin{abaqusdeck}
** Abaqus has no MODEL wrapper.
*NODE
1, 0., 0., 0.
2, 10., 0., 0.
\end{abaqusdeck}
\end{dialectexamples}

\notesheading

The model marker is deliberately optional so existing compact FEMaster decks remain valid. It should not be confused with \cmd{PART}: \cmd{PART} creates a reusable topology namespace, whereas \cmd{MODEL} only marks the root model context.

\keywordpage{PART}

\cmd{PART} begins a reusable finite-element topology definition. The command creates a named Part and makes it the active topology container. Nodes, elements, part-level sets, part-level surfaces, and section assignments that follow are stored relative to this Part until \cmd{END PART} closes the scope.

Part-local identifiers are intentionally sparse and local. Node 1 in one Part and node 1 in another Part are unrelated objects. The Part has no assembly placement; all coordinates remain in the Part reference system. Reusing a component therefore does not require copying or renumbering its topology. Instead, each \cmd{INSTANCE} references the same Part and contributes a rigid placement during compilation.

Explicit Parts are optional in native FEMaster input. Root-level nodes and elements are stored in the default Part. This means a one-component model can remain flat without losing access to the same solver architecture. Abaqus-style decks commonly use explicit Parts, and the supported Abaqus reader maps them to the same Part objects used by native FEMaster input.

\begin{keywordparameters}
\key{NAME} & required & Unique name of the reusable Part. The name is referenced by \cmd{INSTANCE}. \\
\end{keywordparameters}

No data line belongs directly to \cmd{PART}; the body consists of nested model-definition commands.

\exampleheading

\begin{dialectexamples}
\begin{femasterdeck}
*PART, NAME=BLOCK
*NODE
1, 0., 0., 0.
2, 10., 0., 0.
*ELEMENT, TYPE=T3, ELSET=BAR
1, 1, 2
*END PART
\end{femasterdeck}
\begin{abaqusdeck}
*PART, NAME=BLOCK
*NODE
1, 0., 0., 0.
2, 10., 0., 0.
*ELEMENT, TYPE=T3D2, ELSET=BAR
1, 1, 2
*END PART
\end{abaqusdeck}
\end{dialectexamples}

\notesheading

Part-level node sets, element sets, and surfaces are copied through each Instance when the model is compiled. Section assignments remain associated with the part topology and therefore apply to every instance of that Part. Assembly-level sets can later combine entities from multiple instances.

\keywordpage{END PART}

\cmd{END PART} closes the active Part definition and restores the root/default model context. It carries no parameters and no data. Explicit closure is important because subsequent root-level definitions must not accidentally become part-local topology.

The command is shared by native FEMaster and the supported Abaqus reader. Internally the parser deactivates the current named Part and restores the default context used by flat native input. It does not trigger compilation; Parts may be defined and closed before any Instances are created.

\syntaxheading

\begin{syntax}
*END PART
\end{syntax}

\exampleheading

\begin{dialectexamples}
\begin{femasterdeck}
*PART, NAME=PLATE
...
*END PART
\end{femasterdeck}
\begin{abaqusdeck}
*PART, NAME=PLATE
...
*END PART
\end{abaqusdeck}
\end{dialectexamples}

\notesheading

Do not use the native loadcase \cmd{END} as a replacement for \cmd{END PART}. These commands close different scopes and are validated independently.

\keywordpage{ASSEMBLY}

\cmd{ASSEMBLY} begins the assembly context. It is optional in native FEMaster models and is primarily useful when explicit Part Instances or assembly-level sets and surfaces are required. The supported Abaqus reader uses the familiar Abaqus Assembly scope for the same purpose.

Assembly scope is the point at which reusable part topology is referenced rather than redefined. \cmd{INSTANCE} entries select Parts and assign placements. Node sets, element sets, and surfaces defined at assembly level can refer to compiled entities belonging to one or more instances. In contrast, region definitions inside a Part remain part-local and are automatically expanded with the Part.

The assembly itself does not duplicate topology at parse time. Compilation remains the single operation that expands Instances and establishes the dense global model. As a result, the conceptual order is Part definition, Instance placement, compilation, then materialization of assembly-dependent regions.

The native FEMaster Assembly command does not require a name. Abaqus Assembly input commonly includes \key{NAME}; the supported reader accepts the structural Assembly scope according to its registered grammar. The name has no effect on the solver matrices.

\exampleheading

\begin{dialectexamples}
\begin{femasterdeck}
*ASSEMBLY
*INSTANCE, NAME=A, PART=BLOCK
0., 0., 0.
*END INSTANCE
*END ASSEMBLY
\end{femasterdeck}
\begin{abaqusdeck}
*ASSEMBLY, NAME=ASSEMBLY
*INSTANCE, NAME=A, PART=BLOCK
0., 0., 0.
*END INSTANCE
*END ASSEMBLY
\end{abaqusdeck}
\end{dialectexamples}

\notesheading

A model with no explicit Assembly remains valid. The compile step creates the solver-facing model from the default Part in the same way that an explicit instance expands a named Part. Use Assembly syntax for semantic organization, not because the solver requires an Assembly keyword.

\keywordpage{END ASSEMBLY}

\cmd{END ASSEMBLY} terminates the Assembly context. The command carries no mechanical data. After the scope closes, later root-level definitions are no longer interpreted as assembly-level region construction.

Because assembly regions may depend on compiled instance maps, the reader can encounter the structural scope in more than one dependency pass while executing only the callbacks whose dependencies are available. This implementation detail is transparent to the deck: users write one \cmd{ASSEMBLY}/\cmd{END ASSEMBLY} pair.

\exampleheading

\begin{dialectexamples}
\begin{femasterdeck}
*ASSEMBLY
...
*END ASSEMBLY
\end{femasterdeck}
\begin{abaqusdeck}
*ASSEMBLY, NAME=ASSEMBLY
...
*END ASSEMBLY
\end{abaqusdeck}
\end{dialectexamples}

\keywordpage{INSTANCE}

\cmd{INSTANCE} creates a rigid placement of an existing Part. FEMaster intentionally uses the same placement syntax as the supported Abaqus reader. The command requires a unique Instance name and the name of the referenced Part. Up to two data lines then describe the placement: an optional translation vector and an optional axis-angle rotation.

An Instance is lightweight before compilation. It references, rather than copies, the Part. The translation and rotation are stored as an affine rigid transformation. When compilation expands the Instance, every part-local node coordinate \(\boldsymbol X\) is mapped into the assembly coordinate system. For a translation \(\boldsymbol t\) followed by rotation \(\boldsymbol R\) about an axis passing through point \(\boldsymbol p\), the implemented mapping is
\[
\boldsymbol x
=
\boldsymbol R\boldsymbol X
+
\boldsymbol R\boldsymbol t
+
\boldsymbol p-\boldsymbol R\boldsymbol p.
\]
The translation therefore acts first and the axis rotation second, matching the supported Abaqus placement semantics.

The rotation line contains two points that define the global rotation axis followed by the angle in degrees. The two axis points must be distinct and all values must be finite. Rotation is evaluated using the normalized axis and Rodrigues' formula. If only a seven-value line is present, it is interpreted as a rotation without a preceding translation. If only a three-value line is present, it is a pure translation. With no data lines the Instance uses identity placement.

\begin{keywordparameters}
\key{NAME} & required & Unique Instance name. Used to qualify assembly-level references. \\
\key{PART} & required & Name of the previously defined Part that is instantiated. \\
\end{keywordparameters}

\begin{keyworddata}
\val{tx, ty, tz} & Optional translation in global coordinate components. \\
\val{x1,y1,z1,x2,y2,z2,angle} & Optional rotation axis through two global points and angle in degrees. \\
\end{keyworddata}

\exampleheading

\begin{dialectexamples}
\begin{femasterdeck}
*INSTANCE, NAME=RIGHT, PART=BRACKET
100., 0., 0.
0., 0., 0., 0., 0., 1., 90.
*END INSTANCE
\end{femasterdeck}
\begin{abaqusdeck}
*INSTANCE, NAME=RIGHT, PART=BRACKET
100., 0., 0.
0., 0., 0., 0., 0., 1., 90.
*END INSTANCE
\end{abaqusdeck}
\end{dialectexamples}

\notesheading

The source Part remains unchanged regardless of how many Instances reference it. Part-level regions are expanded separately for each Instance. This is the key reason identifiers can stay local and sparse until compilation. A second Instance of the same Part may therefore use a completely different placement without any topology duplication in the input deck.

\keywordpage{END INSTANCE}

\cmd{END INSTANCE} closes an Instance scope. The supported current placement syntax stores all placement information on the \cmd{INSTANCE} command itself; no nodes or elements are normally defined inside the Instance body. The explicit closing keyword is retained because it matches Abaqus structural syntax and makes nesting unambiguous.

No parameters or data lines are accepted. Closing an Instance does not compile it immediately; all semantic Parts and Instances are completed before the one-way compile step expands them.

\exampleheading

\begin{dialectexamples}
\begin{femasterdeck}
*INSTANCE, NAME=A, PART=BLOCK
20., 0., 0.
*END INSTANCE
\end{femasterdeck}
\begin{abaqusdeck}
*INSTANCE, NAME=A, PART=BLOCK
20., 0., 0.
*END INSTANCE
\end{abaqusdeck}
\end{dialectexamples}

\section{Mesh definition}

\keywordpage{NODE}

\cmd{NODE} defines finite-element nodes by sparse user identifier and Cartesian reference coordinates. In a Part scope the nodes belong to that Part. At native FEMaster root level they belong to the default Part, which is why a simple deck can omit all explicit Part and Instance syntax. Node identifiers are not required to form a dense sequence; dense solver rows are assigned only during compilation.

The optional \key{NSET} parameter adds every node defined by this command block to a node set. Its native default is \val{NALL}. Coordinates omitted from the data record default to zero, so two-dimensional or one-dimensional geometries may use shorter records, although explicitly writing all three coordinates often improves readability.

Nodes defined inside separate Parts may reuse the same numerical identifier. Element connectivity inside a Part resolves against that Part's nodes. After instance expansion, compiled identifiers distinguish the otherwise identical local labels.

\begin{keywordparameters}
\key{NSET} & optional & Node set receiving every node in the block. Native default: \val{NALL}. \\
\end{keywordparameters}

\begin{keyworddata}
\val{id} & Sparse node identifier in the active Part. \\
\val{x, y, z} & Cartesian reference coordinates; missing components default to zero. \\
\end{keyworddata}

\exampleheading

\begin{dialectexamples}
\begin{femasterdeck}
*NODE, NSET=EDGE
10, 0.,  0., 0.
20, 25., 0., 0.
30, 50., 0., 0.
\end{femasterdeck}
\begin{abaqusdeck}
*NODE, NSET=EDGE
10, 0.,  0., 0.
20, 25., 0., 0.
30, 50., 0., 0.
\end{abaqusdeck}
\end{dialectexamples}

\notesheading

A node coordinate is part of the undeformed/reference geometry. Prescribed displacement, initial velocity, and nodal transform data do not modify this stored reference coordinate. Instance placement is likewise applied at compilation rather than destructively changing the Part's node table.

\keywordpage{ELEMENT}

\cmd{ELEMENT} defines element topology. Each record contains an element identifier followed by the node identifiers of its connectivity. The required \key{TYPE} parameter selects the formulation and therefore determines the required node count and interpolation. The optional \key{ELSET} parameter inserts each defined element into a named element set; native FEMaster defaults this set to \val{EALL}.

As with nodes, element identifiers remain sparse and local to the active Part until compilation. Connectivity is resolved in the Part's local node namespace. Long higher-order connectivities may span multiple physical input lines where allowed by the grammar.

Native FEMaster and Abaqus input use many identical element labels for solids. Beam and truss naming differs in places, and the Abaqus shell labels are deliberately mapped to the FEMaster FRT shell implementations. In particular, Abaqus \val{T3D2} maps to FEMaster \val{T3}; Abaqus \val{S3/S3R}, \val{S4/S4R}, \val{S6/S6R}, and \val{S8/S8R} map to the corresponding FRT shell implementations. Native FEMaster additionally exposes element formulations such as \val{MITC4}, \val{MITC8}, \val{QSPT}, and explicit \val{MITC*FRT} names.

The supported native element labels are currently
\begin{itemize}
  \item solids: \val{C3D4}, \val{C3D5}, \val{C3D6}, \val{C3D8}, \val{C3D8R}, \val{C3D10}, \val{C3D15}, \val{C3D20}, \val{C3D20R};
  \item line elements: \val{B33} and \val{T3};
  \item shells: \val{S3}, \val{S4}, \val{S6}, \val{S8}, \val{MITC4}, \val{MITC8}, \val{QSPT}, \val{MITC3FRT}, \val{MITC4FRT}, \val{MITC6FRT}, and \val{MITC8FRT}.
\end{itemize}
The Abaqus reader accepts the solid labels above together with \val{B33}, \val{T3D2}, and \val{S3/S3R/S4/S4R/S6/S6R/S8/S8R}.

The five-node pyramid \val{C3D5} is represented internally using the supported eight-node solid topology with the apex repeated in the upper four connectivity slots. This mapping is handled by the reader; users still provide the natural five-node pyramid record.

\begin{keywordparameters}
\key{TYPE} & required & Element formulation/type identifier; accepted values depend on the selected input dialect. \\
\key{ELSET} & optional & Element set receiving all elements in this block. Native default: \val{EALL}. \\
\end{keywordparameters}

\begin{keyworddata}
\val{id} & Sparse element identifier in the active Part. \\
\val{n1, n2, ...} & Part-local node connectivity in the formulation-specific order. \\
\end{keyworddata}

\exampleheading

\begin{dialectexamples}
\begin{femasterdeck}
*ELEMENT, TYPE=T3, ELSET=BARS
1, 1, 2
2, 2, 3

*ELEMENT, TYPE=MITC4, ELSET=PANEL
10, 11, 12, 13, 14
\end{femasterdeck}
\begin{abaqusdeck}
*ELEMENT, TYPE=T3D2, ELSET=BARS
1, 1, 2
2, 2, 3

*ELEMENT, TYPE=S4, ELSET=PANEL
10, 11, 12, 13, 14
\end{abaqusdeck}
\end{dialectexamples}

\notesheading

The element type determines only topology and element formulation. Material and geometric properties are assigned separately through Sections. Consequently, creating a shell or solid element without an appropriate Section leaves the model structurally incomplete even though its connectivity is valid. Detailed formulation-specific node ordering, integration, output quantities, and kinematic assumptions are described in the element theory material retained elsewhere in the manual and source documentation.
