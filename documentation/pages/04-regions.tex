\chapter{Regions and Selections}
\label{chap:regions}

Regions give names to subsets of a finite-element model. They are the connection between topology and nearly every higher-level modelling operation: Sections target element regions, supports and concentrated loads target node regions, pressure and traction loads target surfaces, and constraints and contact use combinations of node and surface regions. A well-structured deck therefore treats sets and surfaces as part of the semantic model rather than as incidental lists of identifiers.

FEMaster distinguishes between regions defined inside a Part and regions defined at Assembly level. Part-level regions store sparse local identifiers and are reusable with the Part. When a Part is instantiated, its regions are expanded through the corresponding local-to-compiled identifier maps. Assembly-level regions are materialized after compilation and can refer to one Instance explicitly or combine already compiled regions from several Instances.

\keywordpage{NSET}

\cmd{NSET} creates or extends a named node region. The same command is used by native FEMaster input and the supported Abaqus reader. The set can contain explicit node identifiers, references resolved at Assembly level, or an arithmetic sequence selected with \key{GENERATE}. The set name is supplied through \key{NSET}; \key{NAME} is accepted as an alternative spelling.

Inside a Part, numeric entries are stored exactly as local node identifiers. No dense global row is assigned at this stage. At Assembly level the situation is different: the semantic topology has already been compiled, so node references are translated through the Instance maps into compiled node identifiers. The optional \key{INSTANCE} parameter qualifies every unqualified target in the command block and is therefore valid only in Assembly scope.

The generated form contains a start identifier, an inclusive end identifier, and an optional increment. The increment defaults to one and may be positive or negative, but it may not be zero. A range whose direction is incompatible with the sign of the increment contributes no entries. Explicit-set input can also reference existing compiled node regions at Assembly level, allowing larger regions to be built from previously named subsets rather than repeating every identifier.

\begin{keywordparameters}
\key{NSET} / \key{NAME} & required & Name of the node set to create or extend. \\
\key{INSTANCE} & optional & Assembly-only Instance qualifier applied to unqualified node references. \\
\key{GENERATE} & optional flag & Interpret each data row as start, end, increment rather than explicit targets. \\
\end{keywordparameters}

\begin{keyworddata}
Explicit targets & Node identifiers or, at Assembly level, resolvable node-set/reference tokens. \\
\val{start, end, increment} & Arithmetic identifier range for \key{GENERATE}; increment defaults to 1. \\
\end{keyworddata}

\exampleheading

\begin{dialectexamples}
\begin{femasterdeck}
*PART, NAME=BEAM
*NODE
1, 0., 0., 0.
2, 1., 0., 0.
3, 2., 0., 0.
4, 3., 0., 0.
*NSET, NSET=ENDS
1, 4
*NSET, NSET=ALLN, GENERATE
1, 4, 1
*END PART
\end{femasterdeck}
\begin{abaqusdeck}
*PART, NAME=BEAM
*NODE
1, 0., 0., 0.
2, 1., 0., 0.
3, 2., 0., 0.
4, 3., 0., 0.
*NSET, NSET=ENDS
1, 4
*NSET, NSET=ALLN, GENERATE
1, 4, 1
*END PART
\end{abaqusdeck}
\end{dialectexamples}

\notesheading

A set name is a stable modelling reference; the numerical IDs inside it are not. In a multi-instance model, use part-level sets wherever the region concept belongs to the component itself. Use Assembly-level sets when the selection is inherently an assembly concept, for example a support region that combines nodes from several placed components.

\keywordpage{ELSET}

\cmd{ELSET} is the element-domain counterpart of \cmd{NSET}. It creates or extends a named element region from explicit element references or generated arithmetic ranges. The command is shared by native FEMaster and the supported Abaqus reader, and \key{NAME} is accepted as an alternative to \key{ELSET} for the set name.

Within a Part, the entries remain sparse part-local element identifiers. This is the representation used by part-level section assignments and by part-level surfaces that refer to an element set. At Assembly level, entries are mapped to compiled global element rows. The optional \key{INSTANCE} qualifier resolves local element labels against one specific Instance; without it, targets must already be unambiguous in the compiled Assembly reference space.

As with node sets, \key{GENERATE} uses an inclusive start/end/increment record. The increment defaults to one and cannot be zero. Explicit Assembly entries may refer to previously defined element sets as well as individual resolvable elements, making it possible to form union-style regions without enumerating all members again.

\begin{keywordparameters}
\key{ELSET} / \key{NAME} & required & Name of the element set to create or extend. \\
\key{INSTANCE} & optional & Assembly-only Instance qualifier for local element references. \\
\key{GENERATE} & optional flag & Generate an arithmetic sequence of element identifiers. \\
\end{keywordparameters}

\begin{keyworddata}
Explicit targets & Element identifiers or Assembly-level references to resolvable element regions. \\
\val{start, end, increment} & Inclusive generated sequence; increment defaults to 1 and must be nonzero. \\
\end{keyworddata}

\exampleheading

\begin{dialectexamples}
\begin{femasterdeck}
*ELSET, ELSET=DESIGN_DOMAIN, GENERATE
1, 100, 1

*ELSET, ELSET=ODD_ELEMENTS, GENERATE
1, 99, 2
\end{femasterdeck}
\begin{abaqusdeck}
*ELSET, ELSET=DESIGN_DOMAIN, GENERATE
1, 100, 1

*ELSET, ELSET=ODD_ELEMENTS, GENERATE
1, 99, 2
\end{abaqusdeck}
\end{dialectexamples}

\notesheading

Element sets are the normal target of Section assignments. If the same Part is instantiated several times, a part-level Section assignment follows every copy automatically. An Assembly-level \cmd{ELSET} should therefore be used for a Section only when the intended property truly differs between compiled instances and the corresponding Section grammar permits such an assignment.

\keywordpage{SURFACE}

\cmd{SURFACE} constructs geometric boundary entities from element sides. A surface is not merely a list of nodes: it retains the element-side relationship required to evaluate normals, surface Jacobians, tractions, pressure loads, coupling weights, tie projections, and contact geometry. Depending on the source element, a requested boundary may produce a two-dimensional surface entity or a line entity.

Native FEMaster permits two closely related data forms. The explicit-ID form contains a user surface identifier, an element identifier, and a side token. The target form contains an element or element-set reference followed by the side token; FEMaster creates all corresponding boundary entities and inserts them into the surface set named by \key{SFSET} or \key{NAME}. The default set name is \val{SFALL}. At Assembly level only the target form is meaningful because compiled boundary identifiers are generated during materialization rather than chosen as sparse user IDs.

Side tokens accept plain integer face numbers, the conventional \val{S1}, \val{S2}, \ldots form, and the shell-side aliases \val{SPOS} and \val{SNEG}. \val{SPOS} maps to side 1 and \val{SNEG} to side 2. If a target names an element set, the selected side is created for every element in that set.

At Assembly level \key{INSTANCE} can qualify the target. The reader first resolves a qualified element set if one exists and otherwise resolves the token as one compiled element reference. This makes the same semantic surface definition usable whether it selects one face or a complete face family.

The supported Abaqus reader registers its own \cmd{SURFACE} grammar but materializes surfaces into the same FEMaster boundary representation. Abaqus-style examples should therefore use the supported element-based surface form rather than relying on arbitrary surface features from the full Abaqus product that are outside FEMaster's reader.

\begin{keywordparameters}
\key{SFSET} / \key{NAME} & optional & Destination surface-set name. Native default: \val{SFALL}. \\
\key{INSTANCE} & optional & Assembly-only qualifier for the target element or element set. \\
\end{keywordparameters}

\begin{keyworddata}
\val{surface_id, element_id, side} & Native part/root form with an explicit sparse surface identifier. \\
\val{target, side} & Element or element-set target followed by a side token; valid at Part and Assembly level. \\
\end{keyworddata}

\exampleheading

\begin{dialectexamples}
\begin{femasterdeck}
*SURFACE, NAME=TOP
SOLIDS, S2

*SURFACE, NAME=ONE_FACE
17, 42, S1
\end{femasterdeck}
\begin{abaqusdeck}
*SURFACE, NAME=TOP, TYPE=ELEMENT
SOLIDS, S2
\end{abaqusdeck}
\end{dialectexamples}

\notesheading

The geometric direction associated with a side is determined by the element formulation and its connectivity. Loads and contact should therefore target the intended element side rather than attempting to infer a normal direction from an unordered node set. For shells, positive and negative faces distinguish the two sides of the midsurface.

\keywordpage{SFSET}

\cmd{SFSET} groups existing surface identifiers into a reusable surface region. It is a native FEMaster convenience command: whereas \cmd{SURFACE} creates boundary geometry from elements, \cmd{SFSET} collects already existing surface entities. This distinction matters for models in which explicit sparse surface IDs are used or several independently created surfaces should be combined into one target.

The command accepts \key{SFSET} or \key{NAME} as the destination name; if neither is supplied the native default is \val{SFALL}. Entries may be explicit references or generated ranges selected with \key{GENERATE}. At Part level the values remain sparse local surface identifiers. At Assembly level they are resolved through the compiled surface maps, optionally qualified by \key{INSTANCE}.

The generated form follows the same start/end/increment convention as \cmd{NSET} and \cmd{ELSET}. The increment defaults to one and may be negative but not zero. Explicit Assembly-level entries can also merge existing compiled surface sets where the reference resolver can identify them.

The Abaqus reader does not register a separate \cmd{SFSET} keyword. Abaqus input normally names a surface directly with \cmd{SURFACE}; the resulting named surface already serves as the reusable region. The side-by-side example therefore shows the equivalent modelling intent rather than inventing unsupported Abaqus syntax.

\begin{keywordparameters}
\key{SFSET} / \key{NAME} & optional & Destination surface-region name; native default \val{SFALL}. \\
\key{INSTANCE} & optional & Assembly-only Instance qualifier. \\
\key{GENERATE} & optional flag & Generate surface identifiers from an arithmetic range. \\
\end{keywordparameters}

\begin{keyworddata}
Explicit targets & Existing surface identifiers or resolvable Assembly surface-region references. \\
\val{start, end, increment} & Inclusive generated surface-ID sequence; increment defaults to 1. \\
\end{keyworddata}

\exampleheading

\begin{dialectexamples}
\begin{femasterdeck}
*SURFACE, NAME=PATCH_A
101, 20, S1
102, 21, S1
*SURFACE, NAME=PATCH_B
103, 22, S1

*SFSET, NAME=CONTACT_FACE
101, 102, 103
\end{femasterdeck}
\begin{abaqusdeck}
** Abaqus input names the combined
** surface directly.
*SURFACE, NAME=CONTACT_FACE, TYPE=ELEMENT
20, S1
21, S1
22, S1
\end{abaqusdeck}
\end{dialectexamples}

\notesheading

Prefer creating a named \cmd{SURFACE} directly when all required boundaries can be expressed from element or element-set targets. \cmd{SFSET} is most useful when explicit surface IDs already exist, when programmatic deck generation naturally creates surfaces in separate blocks, or when a later union of surface regions improves model readability.
